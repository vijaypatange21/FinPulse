ML Models & Input/Output
FinPulse will use a multi-model architecture with five ML components. For each model we define its
inputs, outputs, and suggested algorithms:
• 1. Financial Health Score (Regression):
• Inputs: Borrower profile + aggregated banking metrics – e.g. monthly income, total expenses,
savings rate, cash-flow volatility, EMI/Income ratio, average balance, credit history length.
• Outputs: A numeric Health Score (0–100) and a categorical risk label (Low/Medium/High).
• Approach: A supervised regression model (e.g. XGBoost or Random Forest) is ideal for handling
non-linear patterns in tabular data. Gradient-boosted trees are “excellent” for credit features 1 .
(Logistic regression can serve as a simple baseline).
• 2. Loan Default Risk (Binary Classification):
• Inputs: The Health Score (above) plus other risk indicators – e.g. missed EMIs count, EMI/Income
ratio, income variance, expense spikes, number of active loans.
• Outputs: A default probability (0–1) and a label (Safe / Watch / High Risk).
• Approach: A supervised classifier (e.g. XGBoost/LightGBM classifier). Boosting models are proven in
credit risk settings 1 .
• 3. Transaction Anomaly/Fraud Detection (Unsupervised):
• Inputs: Raw transaction features – e.g. txn amount, time of day, merchant category, balance after
transaction, frequency patterns.
• Outputs: An anomaly score or flag for each transaction. (No direct “target” label required during
training.)
• Approach: Unsupervised outlier models like Isolation Forest (or One-Class SVM / autoencoder) to
flag sudden abnormal transactions.
• 4. Cash-Flow Forecasting (Time-Series Regression):
• Inputs: Historical balance series (daily or weekly), salary cycles, recurring expenses, EMI dates.
• Outputs: Predicted account balance over the next 7–30 days and warning flags if balance may hit zero
(EMI failure risk).
• Approach: Time-series models (e.g. ARIMA for simplicity, or LSTM neural nets for complex patterns).
• 5. Wellness Recommendation (Rule/Tree-based):
1• Inputs: Summary financial metrics – e.g. savings rate, category spending ratios, debt ratio, current
risk level.
• Outputs: Actionable advice (discrete categories) like “Reduce X spending” or “Increase savings by Y%”.
• Approach: A simple decision tree or rule-based engine, possibly with association-rule mining, to
generate explainable recommendations.
These models are connected. For example, raw transactions feed the Health Score and Anomaly models; the
Health Score feeds into Default Risk; risk outputs and spending trends feed the Wellness model. In this
design, the Health Score and Default Risk models are core (must-have), while the Forecast and Wellness
modules are advanced enhancements.
Data Processing & Feature Pipelines
Raw financial data must be transformed into model-ready features. We propose the following data flow:
1. Data Ingestion: Collect raw inputs (bank statements, transactions, credit bureau data, etc.) into a
data lake or database.
2. Preprocessing: Cleanse and standardize data (e.g. parse dates, handle missing values, encode
categories).
3. Feature Computation: Aggregate transactions by period. For example, compute monthly totals for
income, expenses, savings, EMI payments, and volatility measures. Derive ratios (EMI/Income,
savings rate) and flags (e.g. “expense spike” boolean).
4. Feature Store (Batch & Real-Time): Store features in a structured form. A modern system uses a
dual-store approach: an offline store (historical features for model training) and an online store
(real-time features for live scoring). This ensures consistency between training and inference 2 3 .
In practice, batch jobs (e.g. nightly Spark jobs) populate the offline feature tables, while streaming
processors update an in-memory online store with the latest values.
2Figure: A typical feature-store architecture (here using Feast): Spark/SQL jobs compute features into an offline
store, and streaming/ingestion jobs update an online store. The offline store feeds model training, while the online
store serves real-time inference 2 3 . In FinPulse, transaction data is cleaned and aggregated daily (offline)
and recent updates (e.g. latest balance) are kept online. This ensures training and live predictions use the same
feature definitions.
Such pipelines ensure repeatability and low-latency access. In summary, the end-to-end flow is: Raw Data
→ ETL (cleaning/aggregation) → Feature Store → Model Input.
Model Training & Inference Deployment
For each model, we build separate training and inference pipelines:
• Training Pipeline: Uses historical data and the offline feature store. Steps include dataset assembly,
train/validation split, model fitting (with hyperparameter tuning), and evaluation. For example, we
might train the Health Score and Risk models on months of transactional data. We should track
metrics like RMSE (for score) or AUC/KS (for default risk) over time. After training, models and their
metadata go into a model registry. In practice, jobs can be orchestrated via Airflow/Prefect.
• Inference Pipeline: Runs in real time or batch to score new data. For online inference (e.g.
computing current Health Score or flagging anomalies), the service fetches the latest features from
the online store and applies the trained model. Each model is typically exposed as a microservice or
API endpoint. For robust deployment, each model endpoint runs in its own container/runtime (so
upgrades to one ML library don’t break others) 4 . Monitoring modules track latency and accuracy
drift.
Model Choices: In FinPulse’s context, industry best-practices apply. For credit-related predictions, gradient
boosting models (XGBoost/LightGBM) “perform excellently” on tabular risk data 1 , while logistic
regression provides an interpretable benchmark. Unsupervised anomaly detection and simple decision
trees require less “heavy” infrastructure.
Overall, this multi-pipeline architecture yields a scalable system. In fact, ML experts note that a well-
designed architecture “helps teams build scalable, dependable, and efficient machine learning systems” 5
and can ensure the “integrity and safety of the ML infrastructure” 6 .
